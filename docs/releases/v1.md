# Anvia Package Release Policy

Anvia public packages version independently. A change to Studio, a provider, an integration, or
another leaf package does not advance unrelated package versions. Changesets may still include a
dependent package when its published dependency metadata must change.

## npm Channels

- `latest` contains stable package releases.
- `rc` contains independently versioned release candidates prepared from `staging`.
- `preview` contains commit-scoped builds for packages in the pending Changesets release plan.

Applications may use different package versions when their declared dependency ranges are
compatible. Internal workspace dependencies remain `workspace:*` in source and are packed as the
exact version present in the release workspace.

## Changesets

Every public behavior change declares the owning package in a changeset. The Changesets
configuration has no fixed or linked groups. The generated `Version Packages` pull request must be
reviewed before merge; it should contain only directly changed packages and any dependents that
Changesets determines require a release.

Merging a feature pull request does not publish packages. Merging the generated version pull
request consumes the pending changesets and records each planned package version and changelog.

## Stable Publishing

Stable releases use a manual dispatch of `.github/workflows/release.yml` from `main` with the
`stable` channel. The workflow validates that:

- no changesets remain pending;
- every public package has a stable semantic version;
- internal workspace dependencies use `workspace:*`; and
- the complete build, typecheck, test, and package-verification suite passes.

The publisher checks npm before packing. Versions already present on npm are skipped. Only newly
published package versions receive tags and GitHub Releases. If publishing previously succeeded but
tag creation did not, a retry may recover a missing tag without retagging unchanged packages.

Package tags use the package name and version, for example:

```text
@anvia/studio@1.0.3
@anvia/core@1.1.0
```

## Release Candidates

Release candidates are also independent:

1. Target `staging` and add changesets for the packages being tested.
2. Run `pnpm rc:enter` for the first candidate, or `pnpm rc:version` for another candidate.
3. Commit and merge the generated prerelease state into `staging`.
4. Dispatch `.github/workflows/release.yml` from `staging` with the `rc` channel.

Only packages in the prerelease plan receive versions such as `1.0.3-rc.0` and publish under the
npm `rc` tag. Stable packages in the same workspace remain unchanged and are skipped. Run
`pnpm rc:exit` when the independently versioned candidates are ready to return to stable versions.

## Preview Publishing

Preview publishing is manually dispatched from `staging`. The preview preparation script reads the
Changesets release plan and rewrites only planned public packages. Each preview is based on that
package's planned next stable version, for example:

```text
1.0.3-preview.20260825T120000.sha-abcdef0
```

Preview publishing does not create package tags or GitHub Releases.

## Authentication

All package publication runs through `.github/workflows/release.yml` using npm Trusted Publishing.
The `publish` job uses the `npm-publish` GitHub environment and a short-lived OIDC credential. Do
not add npm write tokens or run publication from a local machine.
