# Anvia 1.0 Release Policy

Anvia 1.0 is in release-candidate validation. The v0 line remains supported for maintenance while
1.0 completes its final soak.

## npm Channels

- `rc` points to the current synchronized 1.0 release candidate. New applications and 1.0 testers
  should install every Anvia package from this channel.
- `latest` continues to point to v0 until 1.0 reaches general availability.
- When 1.0 reaches GA, `latest` will move to 1.0 and the maintained v0 releases will use the `v0`
  tag.

Install the 1.0 release candidate:

```sh
pnpm add @anvia/core@rc @anvia/openai@rc
```

Install the stable v0 line before 1.0 GA:

```sh
pnpm add @anvia/core@latest @anvia/openai@latest
```

After 1.0 GA, applications intentionally remaining on v0 should use:

```sh
pnpm add @anvia/core@v0 @anvia/openai@v0
```

Do not mix release channels. Anvia packages are released as one synchronized train and their
internal contracts are only supported when the package versions belong to the same release.

## Support Policy

The v0 line receives security fixes, correctness fixes, and narrowly scoped compatibility fixes.
It does not receive new features, new integrations, or public API redesigns.

The v1 line is the active development baseline. During the final release-candidate freeze, changes
are limited to release blockers, documentation corrections, and test coverage needed to validate
the candidate.

## Seven-Day Candidate Soak

The soak begins only after all synchronized packages for one candidate are published under `rc`,
the matching Git tag identifies the exact release commit, and the complete release workflow has
passed.

During the soak:

- No features or public API changes enter the candidate branch.
- No runtime, dependency, packaging, or generated-artifact change is added to the candidate.
- Release-blocking defects are fixed on a pull request, validated through the complete workflow,
  and published as a new RC.
- Publishing a replacement RC resets the full seven-day clock. Time spent testing an earlier RC
  does not carry forward.
- Documentation or test-only changes that do not alter the published artifacts may continue, but
  they must still pass CI.

Testing should cover real provider calls, browser and sandbox lifecycle, memory and retrieval
adapters, MCP transports, Studio workflows, packaged imports, abort behavior, retries, and resource
cleanup. Findings should include the exact RC version and a minimal reproduction.

## Source Branches

Before GA:

- `main` is the v0 maintenance branch.
- `staging` is the v1 release-candidate branch and accepts only release blockers during the soak.

At GA, preserve the current v0 history as a dedicated `v0` maintenance branch and make the v1 line
the repository's `main` branch. Future features target `main`; v0 fixes target `v0` and publish
under the npm `v0` tag.

Branch renaming and default-branch changes happen only during the GA promotion. They are not part
of cutting or testing an RC.

## GA Gate

Promote 1.0 only when one exact RC has completed seven uninterrupted days with no open release
blocker and its build, typecheck, tests, packaging checks, and release workflow are green. GA uses
the already validated source commit; it must not introduce a last-minute code or dependency change.
